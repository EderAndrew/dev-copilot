# ADR-004 — Armazenamento local cifrado (SQLCipher + cofre do SO)

- **Status:** Proposto (macOS verificado localmente; Windows e Linux aguardam a execução do CI)
- **Data:** 2026-10-28
- **Decisores:** Equipe do projeto Dev Copilot
- **Referências:** Constitution v1.1.0 (Art. IV.12), ADR-001, spec 001 (FR-039a, FR-042, SC-018),
  research.md R8/R9, spike S3 (T011)

## Contexto

Transcrições, registros e perguntas são sensíveis e devem ser persistidos cifrados, com a chave fora dos
dados e nunca embutida no aplicativo (FR-039a, Art. IV.12). Sem cofre de credenciais do SO disponível, o
aplicativo não grava conteúdo e bloqueia a captura. A clarificação Q-04 rejeitou depender apenas da
criptografia de disco do SO.

## Opções consideradas

| Opção | Prós | Contras |
|-------|------|---------|
| **SQLCipher (rusqlite `bundled-sqlcipher`) + chave no cofre do SO (`keyring`)** | banco inteiro cifrado (inclui índices e WAL); consultas SQL normais; um mecanismo verificável por SC-018 | dependência nativa de criptografia por SO; exclusão segura limitada em SSD |
| Cifrar campo a campo na aplicação | sem dependência nativa extra | impede consultas/ordenação; criptografia própria; metadados em claro |
| Chave por sessão (crypto-shredding) | exclusão criptográfica forte | gestão de muitas chaves no cofre; complexidade prematura |
| Somente criptografia de disco do SO | zero código | rejeitada na Q-04; não protege contra outros usuários/processos com acesso ao arquivo |

## Decisão

1. SQLite via `rusqlite` 0.41 com SQLCipher embutido. Backend criptográfico do SQLCipher por SO:
   - **macOS**: CommonCrypto (`Security.framework`), selecionado automaticamente pelo `libsqlite3-sys`
     quando `OPENSSL_DIR` não está definido. Nenhuma OpenSSL é ligada (verificado com `otool -L`).
   - **Linux**: `libcrypto` do sistema (OpenSSL 3; pacote `libssl-dev` no build, `libssl3` em runtime).
   - **Windows**: OpenSSL compilada e ligada estaticamente (`bundled-sqlcipher-vendored-openssl`, alvo
     `cfg(windows)` em `crates/persistence/Cargo.toml`), pois não há `libcrypto` de sistema. Requer Perl no
     build (presente nos runners `windows-latest`); NASM é opcional.
2. Chave aleatória de 256 bits gerada na primeira execução e guardada no cofre do SO via `keyring` 4 (modo
   `v1`): Keychain (macOS), Credential Manager (Windows), Secret Service via zbus (Linux).
3. A chave é aplicada como chave bruta com `PRAGMA key = "x'<64 hex>'"` executado por `execute_batch`
   antes de qualquer outra instrução. **Achado do spike**: aplicá-la com `Connection::pragma_update` produz
   uma chave diferente da usada na reabertura (`file is not a database`); não usar `pragma_update` para a
   chave.
4. Pragmas após a chave: `secure_delete=ON`, `journal_mode=WAL`, `foreign_keys=ON`. Arquivo no diretório de
   dados do app com permissões somente do usuário (`0600` em Unix).
5. Cofre indisponível ou chave ausente com banco existente → erro distinto (`secret_store_unavailable`);
   nenhuma gravação e captura bloqueada. Uma chave nova só é gerada quando o banco ainda não existe.

## Resultado do spike S3

Teste descartável: `crates/persistence/tests/spike_sqlcipher.rs` (cifra com chave bruta; o arquivo não contém
o texto nem o cabeçalho `SQLite format 3`; chave correta lê; chave errada falha; ida e volta da chave pelo
cofre real com `DEVCOPILOT_KEYRING_SPIKE=1`).

| SO | Build | SQLCipher | Cofre real | Observação |
|----|-------|-----------|------------|------------|
| macOS (Apple Silicon, local) | ✅ | ✅ | ✅ Keychain | CommonCrypto; sem prompt para item criado pelo próprio binário |
| Windows (`windows-latest`) | pendente CI | pendente CI | pendente CI | OpenSSL vendorizada |
| Linux (`ubuntu-latest`) | pendente CI | pendente CI | pendente CI | `gnome-keyring` em `dbus-run-session` no CI |

Este ADR passa a **Aceito** quando as três linhas estiverem verdes no CI (critério de saída do S3 em
research.md). Se Windows ou Linux falharem, a decisão volta para clarificação (sem alternativa aceita,
plan.md "Riscos e spikes").

## Consequências e tradeoffs

- Build nativo diferente por SO; Windows compila OpenSSL (build mais lento, sem DLL extra na distribuição).
- Linux depende de um provedor de Secret Service ativo (GNOME Keyring, KWallet ≥ 5.97); sem ele, o app
  recusa gravar e explica o motivo (FR-039a).
- Perder a entrada no cofre torna o banco ilegível. Isso é intencional (sem chave de recuperação no MVP) e
  deve ser comunicado em `docs/local-data.md`.
- Atualizações de segurança da OpenSSL vendorizada passam a ser responsabilidade do projeto (`cargo audit`).

## Limitações de exclusão

`secure_delete=ON` sobrescreve páginas liberadas e o WAL recebe checkpoint após a exclusão, mas não há garantia
de remoção física em SSD (wear leveling), snapshots do sistema de arquivos ou backups do SO (Time Machine,
Histórico de Arquivos, snapshots Btrfs/ZFS). Os dados nessas cópias continuam cifrados com a mesma chave
enquanto ela existir no cofre. Essas limitações são exibidas ao usuário antes da exclusão (FR-042).

## Gatilhos de revisão

- Falha do spike em Windows ou Linux no CI.
- Advisory relevante em SQLCipher, OpenSSL vendorizada ou `keyring`.
- Pedido de exclusão criptográfica por sessão, backup/sincronização ou acesso multiusuário.
- Mudança de formato de página/KDF do SQLCipher que exija migração do arquivo.
