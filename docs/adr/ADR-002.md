# ADR-002 — Captura de áudio do sistema por SO

- **Status:** Proposto — spike S1 pendente em hardware real; nenhuma plataforma validada
- **Data:** 2026-10-28
- **Decisores:** Equipe do projeto Dev Copilot
- **Referências:** Constitution v1.1.0 (Art. I.4, V.2), ADR-001 (pendência "disponibilidade de loopback"),
  spec 001 (US8, FR-013, FR-014, FR-016), research.md R2, tasks T150–T155

## Contexto

O áudio dos outros participantes, reproduzido pelo computador, aumenta muito o valor das sessões (US8), mas
os mecanismos, permissões e versões mínimas variam por SO e não podem ser assumidos equivalentes (Art. V.2).
Enquanto uma plataforma não for validada, a fonte "áudio do sistema" aparece como indisponível com motivo
(`not_validated_on_platform`) e a sessão com microfone continua possível (FR-014, US8.2).

## Estado atual (sem decisão de adaptador)

- `crates/audio/src/system/mod.rs` registra, em todas as plataformas, uma fonte indisponível com
  `not_validated_on_platform` (`VALIDATED_ON_THIS_PLATFORM = false`). Ela nunca dispara prompt de
  permissão nem capta áudio (teste `crates/audio/tests/availability.rs`).
- O pipeline já suporta duas fontes: cada chunk leva sua fonte, os transcritores segmentam por fonte, os
  trechos finais são marcados por fonte quando há duas (FR-016), e uma fonte que falha ao abrir ou durante a
  captura é informada (`source_status`) enquanto a outra continua (US8.3; `crates/application/tests/dual_source.rs`).
- Nenhuma alteração em `Info.plist`/entitlements foi feita: dependem da opção escolhida para macOS.

## Opções a avaliar no spike S1

| SO | Opção | Permissão / requisito | Observações |
|----|-------|-----------------------|-------------|
| macOS | Core Audio process taps (`AudioHardwareCreateProcessTap`) | macOS 14.4+; permissão de gravação de áudio do sistema (`NSAudioCaptureUsageDescription`) | FFI C/Objective-C com `unsafe` isolado; não exige permissão de gravação de tela |
| macOS | ScreenCaptureKit (áudio de `SCStream`) | macOS 13+; permissão de gravação de tela | `objc2`; prompt de gravação de tela é mais intrusivo para o usuário |
| Windows | WASAPI loopback via `cpal` (stream de entrada no dispositivo de saída padrão) | sem permissão separada | validar troca de dispositivo de saída (FR-011: nunca trocar silenciosamente) |
| Linux | fonte "monitor" do PulseAudio/PipeWire via `libpulse-binding` | depende da sessão; sandbox (Flatpak/Snap) | validar em PipeWire com `pipewire-pulse`, Wayland e X11 |
| Linux | API nativa do PipeWire | idem | mais dependências; avaliar só se a opção via Pulse falhar |

## Protocolo do spike (por SO da matriz R16)

Cada linha só é aprovada quando todos os itens passam em hardware real, registrados aqui com versão do SO,
hardware e data:

1. Captura de 10 min de áudio reproduzido (vídeo de referência) com microfone simultâneo, sem perdas
   perceptíveis; transcrição dos dois lados marcada por fonte.
2. Permissão: estado consultável sem prompt; prompt somente ao iniciar; negar e revogar durante a captura
   interrompem só a fonte do sistema, com orientação (FR-009, FR-010).
3. Troca do dispositivo de saída padrão durante a captura: a fonte é dada como perdida e não troca
   silenciosamente (FR-011).
4. Suspensão/bloqueio da sessão do SO: a fonte é dada como perdida, sem crash.
5. Callback de tempo real só escreve no buffer limitado (Art. V.3); CPU adicional medida.
6. Para macOS: blocos `unsafe` revisados, cada um com `// SAFETY:`, e testes focados do adaptador (Art. I.4).

## Decisão

Pendente. Até a aprovação, nenhuma plataforma registra adaptador real e a opção permanece indisponível com
motivo. Aprovar uma plataforma consiste em implementar seu adaptador em `crates/audio/src/system/<so>.rs`
(T151–T153), selecioná-lo em `system::system_source()` sob `cfg(target_os)` e ajustar
`Info.plist`/entitlements quando a opção exigir (T155).

## Gatilhos de revisão

- Resultado do spike S1 em qualquer SO da matriz.
- Mudança de APIs de captura do SO (ex.: novas exigências de permissão no macOS).
- Inclusão de nova plataforma na matriz R16.
